# Authentication Session Guard Contract

## Purpose

`modules/auth_session_guard.py` is an isolated, fail-closed adapter contract.
It re-reads the authenticated user through a trusted server-side callback,
checks current account-active status, and obtains the current server-side
session reference and generation. It returns an immutable snapshot only when
all checks succeed.

## Required integration contract

The future app integration must supply four trusted server-side callbacks:

1. `current_user_fn()`: return the current authenticated user from the
   existing server-side authentication layer, never from browser/form input.
2. `auth_session_id_fn()`: return a cryptographically random session ID
   generated by the server at login (for example, 32 random bytes encoded
   with URL-safe base64). It must be non-empty, printable, contain no
   whitespace, and stay within the adapter's 256-character limit. Rotate it
   on every new login and revoke it on logout.
3. `account_is_active_fn(legacy_user_id)`: query the authoritative account
   record on every guard call. Return exactly `True` only when the account
   exists and is active. Database errors, missing rows, and unknown states
   must return false or raise; they must never be treated as active.
4. `session_generation_fn(legacy_user_id)`: read a server-controlled,
   non-negative integer generation. Increment it when password reset,
   global logout, account recovery, or an administrative revocation should
   invalidate prior sessions.

The returned `ActiveAuthSession` binds legacy identity to the session ID and
current generation. The caller must compare that current generation with the
login-time generation stored in trusted server-side session state using
`session_generation_matches()`. A mismatch must invalidate the authentication
session and private unlock record. The caller must then resolve the verified
Phase 1 account mapping and bind Private Lock state to all three values.

## Security boundaries

- This module does not authenticate passwords, mint session IDs, persist
  revocation state, enforce roles, or authorize private-data operations.
- Callback trust is a caller responsibility; never pass user-supplied
  callbacks or values.
- A stable session ID must be generated and stored only in trusted
  server-side session state. A user ID alone is not a session identifier.
- Revalidate account status and session generation before every private
  data read/write, not only when rendering a page.
- Logout must revoke/rotate the session reference and clear private unlock
  state. Account deactivation and global revocation must invalidate sessions.
- Multiple sessions for one account need distinct session IDs. A per-account
  generation supports global invalidation; per-session revocation may require
  a separate server-side session registry.
- Role authorization remains a separate policy check. Staff status does not
  imply access to private user data.

## Tests

`tests/test_auth_session_guard.py` covers successful resolution, repeated
active-status checks, inactive/unknown account failure, missing identity,
invalid session references, generation changes, invalid generations, and
missing trusted callbacks.

## Not yet proven

The tests use fixtures and do not connect to the current Streamlit login
flow, a real database, Supabase, or a staging deployment. The existing app
does not yet provide all four callbacks. Do not wire this adapter into
`app.py` until a staging identity/session design, revocation storage,
rollback plan, and explicit owner approval are in place.
